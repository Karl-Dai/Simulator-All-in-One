# Simulator All-in-One 技术栈统一方案与分阶段计划

**Status:** Approved

日期：2026-11-04
代码依据：套件提交 `56e433e`，以及 `components.lock.json` 固定的四个上游提交。
审阅状态：用户随后明确要求“执行这些计划”，据此开始 P0/P1 实施。
范围说明：首期在套件及其隔离组件副本内验证公共基础。独立版的跨仓库推广按 P2 另行确认，当前不改动各独立仓库的工作副本。

## 1. 目标与边界

降低公共功能的重复维护成本，同时保持一个安装包、八个独立窗口和三平台交付。
保留入口与 Modbus 的 Go/Wails、IEC104/PMU/OPC UA 的 Rust/Tauri，以及各协议实现。
统一工作围绕公共外观接口、少量 Vue 交互组件、构建环境与组件接入规则展开。

本文件包括总体路线和首期“共享基础试点”的具体方案。
后续的组件目录、运行状态反馈、整套自动更新是独立子项目，分别制定设计和验收范围。
本次授权是制定方案和计划；实施、提交、推送、发版和部署的状态分别记录。
用户已授权实施首期计划和使用 Rex 中的 OpenCode 免费模型参与编码。
本次没有提交、推送、发版或部署授权。

现有兼容约束：

- 保持 `SIMLAB_DATA_DIR`、`SimLab` 数据目录、各角色目录及现有应用标识。
- 保持工程、证书、连接参数和各协议状态的归属；公共界面不读取这些数据。
- 套件程序继续由完整套件管理更新；独立版保留自己的更新渠道。
- 关闭入口后，已启动的模拟器继续运行。
- 工作流继续使用 `workflow_dispatch`，即手动触发。
- 独立版和套件版可并存，公共代码接入不迁移或覆盖独立版用户设置。

## 3. 方案比较

| 方案 | 做法 | 收益 | 代价与判断 |
| --- | --- | --- | --- |
| A：逐步抽取共享层，推荐 | 保留两种宿主，统一接口和 Vue 组件 | 按角色改善维护与体验，逐步减少补丁 | 维护两个小型原生适配器 |
| B：保留当前结构，仅增加检查 | 加强补丁、版本和构建检查 | 改动最少 | 公共交互仍重复实现，适合作为准备步骤 |
| C：统一桌面宿主 | 将应用层迁到同一种桌面框架 | 桌面绑定与生命周期可以共用 | 迁移范围大，需要重新验证窗口、更新、数据路径和协议调用 |

采用 A 作为草案默认方案。
没有性能测量证明当前混合技术栈需要整体替换。
如果后续确定要做单窗口工作区或跨协议工程，再单独评估 C。

## 5. P0：固定构建环境

### 5.1 配置与版本选择

新增 `toolchain.lock.json`，记录清单版本、工具的精确版本以及平台适用范围。
覆盖 Node.js、npm、Python、Go、Rust、Wails CLI，以及 Windows 的 NSIS。
先从最近一次成功的完整构建记录提取实际版本；记录不足的工具，在候选环境完成构建后再锁定。
本设计不预设未经验证的新版本，也不将“升级所有依赖”作为交付条件。

Xcode、MSVC、系统 SDK、Linux 原生软件包和运行资源记录实际版本与来源。
首期不承诺不同系统镜像之间的产物字节完全相同。
所有组件仍使用各自的 npm/Cargo 依赖锁文件；Wails 继续采用当前 `v2.14.0`，除非单独验证升级。

### 5.2 文件与行为

| 文件 | 计划变更 |
| --- | --- |
| `toolchain.lock.json` | 新增工具版本配置，成为本地与 CI 的共同来源 |
| `scripts/toolchain.py` | 新增读取清单、检查版本、输出环境记录能力；不自动替换用户环境 |
| `scripts/suite.py` | 构建前检查工具；把工具配置摘要和实际版本写入构建记录 |
| `.github/workflows/*.yml` | 从同一清单配置工具，保留现有手动触发策略 |
| `scripts/revalidate_package.py` | 工具链变更要求重新构建，避免旧产物被标为新环境产物 |
| `README.md`、`README.zh-CN.md` | 更新准备环境、检查命令和支持范围 |

读取清单所需的引导脚本仅使用 Python 标准库。
CI 在安装项目指定工具前可以使用运行器自带 Python 读取 JSON；该引导解释器不参与产品构建。
正式构建前再次核对锁定工具，记录实际使用的可执行文件位置和版本。
工具缺失或版本不符时，错误必须指出目标版本、实际版本及修复命令。

构建记录新增独立的工具链摘要；入口与每个组件的记录都包含它。
工具链清单变化后，旧构建记录失效，不能通过修改元数据继续沿用旧二进制。
原生环境的记录缺失时，产物标为“来源记录不完整”，不能作为新流程的验收产物。

## 6. P1：公共外观接口与宿主适配

### 6.1 最小接口

新增接口版本，明确主题与语言的可选值：

```ts
type Theme = 'system' | 'light' | 'dark';
type Language = 'auto' | 'zh-CN' | 'en';

interface AppearanceV1 {
  schemaVersion: 1;
  theme: Theme;
  language: Language;
}

interface AppearanceReader {
  readAppearance(): Promise<AppearanceV1>;
}
```

接口版本与现有 `launcher.json` 文件版本分别管理。
本期不改变该文件的结构，继续由入口原子写入；子程序只读主题和语言。
不返回收藏、最近使用、工程数据或证书信息。
Go、Rust 和 TypeScript 使用同一组输入输出样例验证默认值与错误行为。

公共前端模块只调用 `AppearanceReader`，由应用启动入口注入具体实现。
Wails 适配器使用生成的绑定；Tauri 适配器使用 `@tauri-apps/api/core` 的公开 `invoke`。
两种 Wails 构建都注册同名外观绑定，避免独立版重新生成绑定时丢失前端模块。
原生构建入口通过 `NewAppearance(false/true)` 决定权限；独立版方法直接返回不支持，不读取套件配置。
新增公共模块不读取 `window.go` 或 `__TAURI_INTERNALS__`。
接口读取失败也不能从套件模式自动切换成独立版模式。

迁移期间保留原 `startSuiteTheme`、Wails `Theme()` 和 Tauri `simlab_theme` 接口。
旧接口保留现有主题解析规则，不改为新外观接口的包装函数。
新接口的文件版本校验和语言默认规则只作用于已迁移的试点。
未迁移的六个角色继续只同步主题，不因缺少语言字段被强制切换成英文。
试点使用新的 `startAppearanceSync` 和外观读取接口。
旧主题脚本作为兼容入口保留到 P2 完成，再移除其中的宿主识别代码。

套件模式沿用当前编译配置，由原生构建标志和匹配的前端构建配置决定。
前端开关不能单独改变原生数据目录、更新权限或应用身份。
独立版不启动套件轮询，也不尝试读取 `launcher.json`。
如果独立版纳入共享范围，它通过自己的适配器使用现有设置来源。

### 6.2 设置同步与默认值

入口保存主题/语言 → 子程序原生适配器读取 → 公共模块验证 → 应用主题与当前有效语言。
旧配置文件缺少 `schemaVersion` 时沿用入口现有规则，视为版本 1；新接口响应缺少版本则报错。
保持当前约 1.5 秒的轮询；隐藏窗口暂停，恢复可见后立即读取，组件卸载时释放监听与定时器。
这一步不增加后台服务、网络端口或跨进程事件中心。

| 输入或故障 | 规定行为 |
| --- | --- |
| 配置文件不存在 | 使用入口既有默认值：`system`、`en` |
| 字段缺失或枚举无效 | 主题回退 `system`，语言回退 `en` |
| `language=auto` | 使用同一解析函数；系统语言以 `zh` 开头时选 `zh-CN`，其他选 `en` |
| JSON 损坏、读取失败、未知文件版本 | 保持最后一次有效值；首次读取则使用默认值；显示可操作提示并抑制重复日志 |
| 未知接口版本 | 视为适配不兼容；保持已有外观并提示修复完整套件 |
| 配置恢复正常 | 下一次读取恢复同步，清除对应故障提示 |

子程序不修复或重写损坏的入口配置；入口继续负责原有备份与恢复逻辑。
关闭入口后，子程序使用最后保存的偏好继续运行。

### 6.3 语言切换的兼容规则

套件语言是当前会话的有效语言，不能覆盖独立版原先保存的语言偏好。
各应用增加不持久化的语言应用方法，例如 `setEffectiveLocale`。
`en` 与上游 `en-US` 等代码的转换由各应用适配器完成。
协议界面继续使用自己的翻译字典；公共组件的文字由调用方传入。

试点接入前逐项核对当前字典覆盖，记录缺失文案。
验收需要检查真实文字变化；只更新 `document.lang` 不算完成。
套件模式下，试点应用的本地语言控件显示“由套件设置管理”，避免两个设置来源互相覆盖。
独立版保留自身设置控件及其持久化行为。

## 7. P1：两个公共 Vue 组件

| 组件 | 公共职责 | 应用负责 |
| --- | --- | --- |
| `StatusBadge` | 标签、语义颜色、忙碌动画、辅助技术可读文本 | 判定连接、运行、可启动等业务状态 |
| `ErrorNotice` | 错误正文、可展开详情、关闭按钮、可选重试按钮及事件 | 发起请求、决定是否可重试、读取诊断信息 |

每个试点各替换至少一处真实状态显示和一处真实错误提示。
组件不能把“进程启动”自动转成“协议已连接”。
错误详情默认作为纯文本渲染，组件本身不执行命令、文件访问或自动重试。
交互控件支持键盘操作；重复刷新相同错误不会持续打断用户。
忙碌动画遵循系统减少动态效果设置。

新组件采用自身作用域样式和带默认值的公共颜色变量。
独立版由本地外观适配提供颜色，不依赖套件脚本设置的页面属性。
接入这两个组件时，不在独立版启用整套旧应用 CSS 覆盖规则。

首期不抽取协议连接表单、点表、报文视图、工程格式或危险操作确认框。
这两项组件足以验证两种宿主共用界面代码的成本和收益。

## 8. 公共代码位置与跨仓库接入

继续以本仓库 `ui/` 为唯一公共源，增加 `contracts/`、`adapters/` 和 `components/` 子目录。
首期保留受控复制方式，扩展 `scripts/sync_ui.py` 与构建前的一致性检查。
共享文件清单集中维护，避免同步脚本和校验脚本各写一份名单。
暂不创建新的共享仓库、包管理体系或公共包发布流程。

每个导出副本记录接口版本、公共源内容摘要及文件清单。
重复同步得到同样结果；手工改动导出副本会在检查时明确报错。
公共文件更新后同步刷新补丁，现有源码和补丁摘要校验继续生效。
文件清单变化时只清理清单声明的旧公共文件，不清理其他上游文件。

| 首期位置 | 职责 |
| --- | --- |
| `ui/contracts/appearance.ts` 与同目录样例 | 定义接口与跨语言测试输入输出 |
| `ui/appearance.ts` | 校验、同步、主题解析与语言通知 |
| `ui/adapters/` | 保存两种宿主适配的公共约定；应用侧注入具体绑定 |
| `ui/components/StatusBadge.vue`、`ErrorNotice.vue` | 公共交互组件 |
| `ui/preferences.go`、`ui/preferences.rs` | 新增只读外观接口，保留旧主题接口 |
| `frontend/src/` | 入口采用共同枚举、默认规则和公共组件 |
| 两个试点的 `master-frontend/src/` | 接入适配器、临时语言覆盖及真实组件使用处 |
| 两个试点的原生应用入口 | 注册新接口，核对套件编译标志与原有配置隔离 |
| `scripts/sync_ui.py`、`scripts/suite.py`、`patches/` | 同步与校验公共源；只对试点增加新行为接入 |

共享文件可以同步到八端，但未迁移角色不导入新的同步入口或交互组件。
未迁移角色也须通过原有构建、启动和深浅主题切换回归。
这些检查用于发现公共样式变化对现有行为的影响。

若覆盖独立版：在各上游以固定版本的源码副本接入公共模块。
独立版正常构建不要求读取套件仓库或用户本机目录。
先在独立版和套件模式分别验证，再将套件接口合入上游并更新套件锁定提交。
同一公共文件在一个构建目标中只加载一次。
公共代码进入上游后，套件补丁移除对应重复内容，不能再次添加同一路径。

若用户选择仅覆盖套件：首期仍使用相同接口与组件，所有集成保留在套件适配副本和补丁中。
该选择不会阻塞 P0，也不会改变两种宿主试点的验收要求。

## 9. 首期工作包与交付顺序

| 顺序 | 工作包 | 依赖 | 完成证据 |

实施时使用隔离的工作副本，不覆盖上游仓库中已有的未提交工作。

P2 建议顺序：两个试点对应的从站 → OPC UA 两端 → PMU 两端。
PMU 的构建工具版本差异单独验证，避免将大版本升级混入界面接入。
推广前为该阶段补充具体方案；不以“试点通过”代替其余六端验收。

## 10. 验收矩阵

| 类别 | 必须验证的场景与结果 |
| --- | --- |
| 工具链 | 缺工具、版本错误、最低版本不兼容均在构建前说明原因；本地与 CI 使用同一配置 |

## 11. 风险与回退

| 风险 | 处理方式 |
| --- | --- |
| 上游语言设置函数会持久化 | 新增仅作用于当前会话的方法，验证原配置前后内容 |
| 公共 CSS 与原有样式竞争 | 保持作用域；按实际使用处迁移，每次核对深浅主题和窄窗口 |
| 上游接入后补丁重复应用 | 同一变更中更新上游提交与剩余补丁；在干净副本应用并构建 |
| 公共改动影响多个应用 | 首期限制在两个试点，推广按角色交付 |
| 新工具版本造成构建回归 | 固定成功版本；依赖升级单列变更，记录每个目标结果 |
| 旧二进制与新来源记录混用 | 工具链与公共源码摘要参与构建记录检查，拒绝不匹配的复用 |

首期保持配置文件结构兼容，不修改用户工程格式。
回退以一组匹配的套件源码、组件提交、补丁和工具链配置为单位重新构建。
用户安装环境恢复应用时仍需先保存并退出相关子程序。
后续若涉及数据格式升级，必须单独规定备份与恢复；更换二进制不代表数据已回退。

## 12. 后续子项目的边界

1. **单一组件目录**：集中协议与角色元数据，生成各语言的检查数据。保持缺组件、未知组件和路径越界检查；不引入动态插件系统。
2. **运行状态反馈**：分别定义程序已启动、窗口可操作、协议已连接。需要实例身份、超时和退出规则，不能复用文件校验状态冒充运行状态。
3. **完整套件更新**：下载、验证、活动进程检查、整体切换、失败恢复和数据兼容独立设计。继续禁止子应用安装独立版更新。

这三项不计入 P1 完成条件，也不随本文件获批而自动进入实施。
