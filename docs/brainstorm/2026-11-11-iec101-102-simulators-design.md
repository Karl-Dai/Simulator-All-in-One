# 在 SAIO 中加入 IEC 60870-5-101 与 60870-5-102 主站和子站

**Status:** Approved

日期：2026-11-11

范围：在 `Simulator-All-in-One` 启动器中新增 4 个角色（101 主站、101 子站、102 主站、102 子站）。代码放在两个新建仓库 `IEC60870-5-101-Simulator` 与 `IEC60870-5-102-Simulator`，两者互相独立。验收要求：同一协议的主站与子站完成一次完整的双向收发。

## 背景

启动器本身是 Go/Wails 程序，8 个模拟器来自 `components.lock.json` 里的 4 个固定仓库，按 commit 克隆到 `.components/` 并打补丁。`scripts/suite.py` 目前硬编码“恰好 8 个角色、4 个仓库”，`internal/suite/catalog.go` 定义角色表。因此新增角色必须指定源码位置，否则打包流水线不会收录。

现有 `IEC60870-5-104-Simulator` 仓库只有 104 的 APCI 实现（`crates/iec104sim-core/src/frame.rs`），没有 FT1.2 链路层，也没有 101 或 102 的 ASDU 差异代码。两个新仓库各自实现自己的链路层与应用层，不引用 104 仓库的 crate，避免跨仓库依赖影响离线打包。

本机曾有一个 egui 写的 102 从站仿真器（`~/Library/Application Support/IEC-60870-5-102-从站仿真器`），源码已不在本机。它说明 102 的中文计量点表与冻结操作是既有使用场景。

## 术语表

| 术语 | 含义 |
| --- | --- |
| ASDU | 应用服务数据单元，规约里真正承载遥信、遥测、遥控等业务数据的那一层 |
| APCI | 104 专用的传输层帧头，含发送序号、接收序号与控制帧 |
| FT1.2 | 101 与 102 使用的链路帧格式，含单字符帧、固定帧、可变帧 |
| PRM | 控制域里的启动标志，1 表示报文由主站（启动站）发出 |
| FCB / FCV | 帧计数位与帧计数有效位，用于识别重发帧 |
| ACD / DFC | 子站应答帧里的“有一级数据待上送”与“链路忙”标志 |
| CoT | 传送原因，说明这条报文是周期上送、突发、召唤应答还是命令确认 |
| CP24 / CP40 / CP56 | 三种时标编码，后面的数字表示占用的比特数 |
| BCR | 累计量的二进制计数读数，4 字节读数加 1 字节标志 |

## 调研结论

### FT1.2 链路层（101 与 102 共用）

104 用 APCI：`68H` 起始、发送序号与接收序号、STARTDT/STOPDT/TESTFR 控制帧。101 与 102 用 FT1.2 链路帧：

| 帧类型 | 字节结构 | 说明 |
| --- | --- | --- |
| 单字符 | `E5H` | 肯定认可 |
| 固定帧 | `10H | C | A | CS | 16H` | 10 字节，地址 1 或 2 字节 |
| 可变帧 | `68H | L L L L | C | A | ASDU | CS | 16H` | `L` 为控制域、地址域与 ASDU 长度之和 |

控制域：`bit0-3` 功能码；`bit4`、`bit5` 在 PRM=1 时表示 FCV、FCB，在 PRM=0 时表示 ACD、DFC；`bit6` 为 PRM；`bit7` 为 DIR。

- 主站方向（PRM=1）功能码：0 复位链路、1 复位 FCB、2/3 发送确认用户数据、4 发送无回答、9 请求链路状态、10 请求一级数据、11 请求二级数据。
- 子站方向（PRM=0）功能码：0 肯定认可、1 否定认可、8 用户数据、11 链路忙。ACD=1 表示子站有一级数据待上送，DFC=1 表示子站缓冲区已满。
- 校验和 `CS` 为控制域到 ASDU 末尾的算术和低 8 位。

非平衡模式下子站不主动发送，只能应答主站的请求。子站有突发事件时在应答帧置 ACD 位，主站看到后发“请求一级数据”取数据。

### 101 与 104 的应用层关系

101 的 ASDU 与 104 相同：监视方向类型 1-40，控制方向 45-51，总召唤 100，计数量召唤 101，时钟同步 103，复位进程 105。差别只在链路层：101 没有发送/接收序号窗口，确认由链路帧完成。104 仓库里的 `decode.rs`、`asdu_encode.rs`、`types.rs`、`data_point.rs` 只作为编码对照，不跨仓库引用。

### 102 与应用层的差异

102 的 ASDU 是独立一套，类型号与 101 冲突：

| 方向 | 类型标识 | 名称 | 说明 |
| --- | --- | --- | --- |
| 子站 → 主站 | 100 | `M_IT_NA_1` | 累计量，无时标 |
| 子站 → 主站 | 101 | `M_IT_TA_1` | 累计量，CP24Time2a |
| 子站 → 主站 | 102 | `M_IT_TB_1` | 累计量，CP40Time2a |
| 子站 → 主站 | 103 | `M_IT_TC_1` | 累计量，CP56Time2a |
| 主站 → 子站 | 120 | `C_IT_NA_1` | 累计量召唤 |
| 主站 → 子站 | 121-123 | `C_IT_TA_1`…`C_IT_TC_1` | 带时标的累计量召唤 |

累计量信息体为 4 字节二进制计数读数加 1 字节标志（顺序号 SEQ 5 位、CY 进位、CA 计数器被调整、IV 无效）。104 的 `M_IT_NA_1` 用相同结构，可对照它的编码实现。102 的传送原因除常规值外还有请求计数量、冻结、计数器变更一组（37、38、40、41、42 附近），与 101 中 37-41 表示分组计数量召唤的含义不同。

### 待核对项

- CP40Time2a（102 的 5 字节时标）的位定义需要在实现前按标准表核对，做成独立编码函数并加固定字节用例，核对结果写入代码注释与验收记录。
- 102 的传送原因码表同样按标准表落地，并允许配置覆盖，便于对接现场变种。

## 目标

1. 启动器里出现 101 主站、101 子站、102 主站、102 子站四个角色，能像现有角色一样启动独立窗口。
2. 101 主站与 101 子站之间完成：复位链路 → 总召唤 → 数据上送 → 遥控确认 → 时钟同步。
3. 102 主站与 102 子站之间完成：累计量召唤 → 读数上送 → 冻结 → 顺序号变化可见。
4. 每个协议的 TCP 与串口共用本仓库的链路层代码。
5. 报文日志能同时显示原始十六进制与逐帧解析，链路统计可见。
6. 不改变 104、Modbus、PMU、OPC UA 的现有行为。

## 方案比较

| 方案 | 分层 | 维护成本 | 结论 |
| --- | --- | --- | --- |
| 101、102 各建独立仓库，各自一份 core 与前端 | 两个仓库互不依赖，构建与发布完全解耦 | FT1.2 与部分 ASDU 代码写两遍，约 800 至 1000 行 | 采用 |
| 新建一个仓库同时放 101 与 102，共用 core | 链路层只写一份 | 两个协议的应用层与界面互相牵制，发布只能整体进行 | 不采用 |
| 扩展现有 104 仓库 | 与 104 共用 core 与构建 | 四个新应用混进 104 的发布节奏，回归面变大 | 不采用 |

重复的 FT1.2 代码用同一套字节用例和状态机用例约束，两个仓库的测试文件名与断言保持对应，改动时能对照。

## 代码分层

两个仓库结构相同，只是协议前缀不同。以 101 为例：

```
IEC60870-5-101-Simulator/
  crates/shared/                套件同步的共享契约文件（preferences、config_store、schema）
  crates/iec101-core/           FT1.2 链路、101 ASDU、会话、传输抽象
  crates/iec101master-app/      101 主站 Tauri 应用
  crates/iec101sim-app/         101 子站 Tauri 应用
  frontend/                     主站与子站共用前端，内含 src/simlab-ui
  Cargo.toml, Cargo.lock
```

`IEC60870-5-102-Simulator` 同构：`crates/iec102-core/`、`crates/iec102master-app/`、`crates/iec102sim-app/`、`frontend/`。

core 的模块划分：

| 模块 | 职责 |
| --- | --- |
| `ft12` | 帧编解码、地址长度变体、校验和、错误分类 |
| `link` | 链路状态机：复位、FCB 翻转、一级/二级数据请求、重发与超时 |
| `session` | 101 为总召唤、计数量召唤、时钟同步、遥控、设点、复位进程；102 为累计量召唤、冻结、计数器复位 |
| `asdu` | 本协议的 ASDU 编码与解码，含时标与品质位 |
| `transport` | TCP 与串口统一接口（串口走 `serialport`），含 pty 测试支持 |
| `config` | 地址长度、地址数值、超时、重试、轮询周期、平衡开关 |

两个 app 只做三件事：读取配置、建立传输、运行会话并把事件推给前端。

## 101 行为设计

主站链路流程：发复位链路（FC=0）→ 收到肯定认可 → 进入轮询 → 周期发请求二级数据（FC=11）→ 子站应答帧 ACD=1 时改发请求一级数据（FC=10）→ 收到数据后回到轮询。FCB 每帧翻转，用 FCB 对比丢弃重复帧。

子站链路流程：收到复位链路回肯定认可并清空发送缓存；收到请求二级数据回当前缓存帧或 `E5H`；一级数据优先于二级数据；缓冲区满时置 DFC=1。

应用层要覆盖的流程：

- 总召唤：类型 100，CoT 20，分激活、激活确认、数据、激活终止四段。
- 计数量召唤：类型 101，CoT 37 起，按分组返回。
- 时钟同步：类型 103，主站下发带 CP56Time2a 的时间。
- 遥控：类型 45/46/47，选择-执行可配置为直接执行。
- 设点：类型 48/49/50。
- 复位进程：类型 105。

## 102 行为设计

数据模型：计量点号（信息对象地址）、4 字节无符号计数读数、顺序号、时标、品质位（CY/CA/IV），费率按现场需要作为可选字段。

流程分三步。主站发 `C_IT_NA_1(120)`，子站按传送原因分组返回 `M_IT_NA_1(100)` 或所选时标类型。主站下发冻结命令后，子站的读数与顺序号发生变化。主站下发计数器复位后，子站把读数清零并置 CA 位。

102 与 101 的代码不共享，`iec102-core` 自己实现 FT1.2 与累计量 ASDU，时标类型可配置，默认 `M_IT_NA_1`，可切换 `M_IT_TA_1`、`M_IT_TB_1`、`M_IT_TC_1`。

## 配置项

主站与子站共用一组参数。地址相关：链路地址长度（1/2 字节）与数值、公共地址长度（1/2）与数值、信息对象地址长度（1/2/3）。时序相关：帧间超时、重发次数、轮询周期、平衡/非平衡开关。传输相关：TCP 端口，或串口名、波特率、数据位、校验位、停止位。

配置沿用套件统一的 SQLite 存储，与其他模拟器一致。

## 界面

一份前端，四个入口，按角色参数切换协议与视图。共有部分包括：连接与串口参数；链路状态与统计（发送帧数、接收帧数、校验错、超时、重发次数）；报文日志（原始十六进制与逐帧解析并列）；点表编辑与 CSV 导入导出；周期与变化上送开关；控制与设点面板；时标与品质位显示。

主站侧多“召唤与控制”面板；子站侧多“点值编辑”与“冻结”面板。102 把遥信/遥测面板换成计量点表面板，列包含计量点号、读数、顺序号、时标、品质位，并提供冻结与复位按钮。

## 仓库与发布

- 两个仓库先建成私有仓库，归属 `Karl-Dai`。当前 `gh` 登录身份已确认是 `Karl-Dai`，对现有组件仓库有 ADMIN 权限。
- 私有仓库意味着 `scripts/suite.py bootstrap` 拉取 commit 和 CI 构建都需要凭证。本机可用 `gh` 配置的 git 凭证，CI 需要 `secrets` 里放一个有读权限的 token，这一项要在第一次远端构建时验证。
- 验收通过后是否转公开由你决定，文档不预设。
- 仓库内提交历史、`Cargo.lock`、`patch` 文件按现有 4 个仓库的做法处理。

## 错误处理

- 链路层错误（校验和错、帧长错、FCB 不符）记入统计并回否定认可或直接丢弃，不中断会话。
- 超时与重发次数按配置执行，连续失败后把链路状态置为断开，界面显示原因，不静默重连。
- 串口打开失败、端口被占用给出明确提示，保留已填参数。
- 102 时标类型不受支持时返回否定确认，并在日志中标明原因。
- 应用层收到未实现的类型标识时记录并忽略，不导致会话退出。

## 风险与不做的事

- 不做 TLS（104 专有）、不做 101/102 文件传输、不做多链路并行。
- CP40Time2a 与 102 传送原因码表依赖标准原文核对。若核对不到，先交付 100/101/103 的可运行流程，并把 102 相关类型标为未完成项。
- 打包脚本的角色数量校验是硬编码，改动同时影响 Windows 便携包与 Linux 自解压包，至少需要一次 macOS 全流程打包验证，其余平台冒烟。
- 组件仓库的 commit 固定机制意味着新代码必须先提交到各自仓库，再更新 `components.lock.json`，两步顺序错会导致构建失败。
- 私有仓库的 CI 读取权限需要在第一次远端构建时验证；若 token 权限不足，构建会停在 clone 阶段。
- 两个仓库各自实现 FT1.2，行为一致性靠同名测试用例保证，改动时必须两边同步。
